# Task B3 - Loops vs Libraries vs SQL

Run: `python compare.py` (output_compare.txt). The data are generated by the program itself (1, 12 and 120 stations x 8,760 hourly readings = a year) into the temporary folder, so no large file is stored in the repository.

## B3.1 Correctness on small data
Daily mean PM2.5 per station by plain loops (csv module + `statistics.mean`), pandas `groupby` and SQL `GROUP BY`, on 2 stations x 365 days = 730 daily means: all three agree within 1e-9 (loops == pandas: True, loops == SQL: True). Example `('S000', '2026-01-01')`: 56.0750 in all three methods.

## B3.2 Increasing the data size (seconds; file reading included for loops and pandas)
| Stations | Rows | Loops (store all + statistics.mean) | Loops (running sum) | pandas groupby | SQL load (once) | SQL GROUP BY query |
|---|---|---|---|---|---|---|
| 1 | 8,760 | 0.017 | 0.011 | 0.007 | 0.013 | 0.004 |
| 12 | 105,120 | 0.256 | 0.118 | 0.042 | 0.126 | 0.044 |
| 120 | 1,051,200 | 2.365 | 1.510 | 0.483 | 1.411 | 0.451 |
Time grows about 10 times for every 10 times more rows in every method, so all are O(n); the difference is the constant: plain loops are about 5 times slower than pandas and SQL. The SQL query itself is as fast as pandas, but the data must be loaded once (1.4 s for a million rows).

## B3.3 Profile of the plain-Python version (cProfile, 12 stations)
Total 0.652 s with 1,395,602 function calls. The function with the largest own time is `csv.DictReader.__next__` (0.184 s, 105,121 calls, 0.300 s with what it calls); next the function `by_loops` itself (0.097 s) and `statistics._sum` (0.048 s own, 0.206 s in total, 4,380 calls from `statistics.mean`, which converts every float to an exact fraction). So reading and parsing the CSV, and the exact-arithmetic mean, are the slow parts. (cProfile adds some time of its own.)

## B3.4 Engineering trade-off
Differences: the loops do the reading, parsing and grouping in interpreted Python; pandas and SQLite do it in compiled code; `statistics.mean` is slow on purpose (exact); SQL needs a load step but then keeps the data and answers many questions without reading the files again.
- Quick one-time analysis: pandas (`read_csv` + `groupby`, 3 lines, fastest here at 0.483 s for a million rows, no database to create).
- Daily automated report: SQLite with `executemany` to add the new day's cleaned rows and an SQL `GROUP BY` query (primary key / index, data checked by the table definition, nothing re-read, the same query every day; the report is reproducible and auditable).

## Alternative concept: running sum and count in one pass
Solution: `sums[(station, day)] = [total, count]`, updated for each row, then `total / count` (`by_running_sum`). Result identical to the first version (checked). Time: O(n) for both; measured 1.510 s against 2.365 s for a million rows, about 1.6 times faster because there is no list building and no exact `statistics.mean`. Space: the first method stores every reading, O(n) (4.60 MB peak for 105,120 rows); the running sum stores two numbers per (station, day), O(stations x days) (1.40 MB peak for 12 stations x 365 days = 4,380 groups). The limit: the running sum cannot give a median or any value that needs all readings.
